# Service on time, at the door step (PRD)

- Author: Abhishek Mehrotra
- Date: 2026-08-10

---

## 1. Background (problem definition)
Customers who own computers or hardware in need of repair currently have no way to request a repair or check its status online. To find out how their repair is progressing, they have to visit or call the service center in person, which is inconvenient for both customers and staff.

---

## 2. Current approach and its limits
Today, repair requests and status updates are handled entirely in person or by phone. Customers must call or visit the service center just to ask "is my device ready yet?", and staff have to interrupt their repair work to answer these inquiries. There is no centralized, self-service way for customers to submit a request or track progress, which wastes staff time and leaves customers without visibility into their repair.

---

## 3. Goals and expected impact (success criteria)
- Reduce phone/in-person status-check inquiries by at least 50%, since customers can look up status themselves.
- Cut average time-to-submit a repair request to under 2 minutes via the online form.
- Achieve 100% accuracy between the actual repair stage and the status shown online (no stale/mismatched statuses); measured via periodic staff spot-checks comparing displayed status against the physical device, since no automated audit tooling is planned for this exercise.
- Support at least the 4 defined repair stages without ambiguity or missing states.

---

## 4. Users and the usage flow
- Users: Customers who own computers/hardware in need of repair.
- Usage flow:
  Customer submits repair request (device type, issue description, phone number, optional photos) → Receives a request ID → Customer looks up status later using request ID + phone number → Sees current stage (Received → In Repair → Ready for Pickup → Completed) → Customer picks up device once status is "Ready for Pickup."

---

## 5. Key features (split into must / nice)

**Must-have**

### 1) Repair Request Submission
- Description: Customers submit a new repair request with their device and issue details.
- Rules the AI must follow:
  - Required fields: device type (fixed dropdown: Desktop, Laptop, Monitor, Printer, Other), issue description (minimum 10 characters, maximum 500 characters), contact phone number (required, 10-digit local number format).
  - If device type is "Other," an additional free-text field appears to let the customer specify the device.
  - Up to 3 photo attachments allowed (optional — 0 is acceptable), JPG/PNG only, each file must be 5MB or smaller.
  - On submission, status is automatically set to "Received."
  - Request ID is auto-generated by the backend as a sequential, auto-incrementing code (format: `RPR-` followed by 6 digits, e.g. `RPR-000001`, `RPR-000002`, ...).

### 2) Repair Status Tracking
- Description: Customers check the progress of their repair request.
- Rules the AI must follow:
  - Status must be exactly one of these 4 stages: Received → In Repair → Ready for Pickup → Completed.
  - Lookup supports two modes, and no name-only search is supported in either: (a) request ID + phone number together — both must match the same request, returning that single record; (b) phone number alone (no request ID) — returns a list of all requests matching that phone number (request ID, device type, and status) so the customer can pick the right one.
  - If a customer loses their request ID, they can still find it via mode (b) above (phone number alone); if that still doesn't identify the right request, they must contact the service center directly so staff can look it up manually.
  - Every status change is logged with a timestamp, so a full status history is available, not just the current stage.

**Nice-to-have**
- None planned for this exercise — see Section 6 (out-of-scope) for features explicitly deferred.

---

## 6. Scope and out-of-scope

**In scope (will be built)**
- Repair Request Submission (see Section 5, Feature 1)
- Repair Status Tracking (see Section 5, Feature 2)

**Out-of-scope (will NOT be built this time)**
- No online payment/invoicing (payment handled in person for now)
- No admin dashboard for staff to manage repairs — staff will update status directly through the Supabase dashboard/database for now
- No customer accounts/login — lookup is by request ID + phone number only, no registration or password system
- No automatic notifications (SMS/email) on status change — customers must manually check the status page for now
- No spam/bot protection (CAPTCHA, honeypot, etc.) on the submission form for this exercise

---

## 7. Security and privacy review
- Document confidentiality: Low — no sensitive business documents are used or exposed by this app.
- Personal data involved: Customer phone number is collected for repair request lookup; this is the only personal data stored. No payment or identity documents are collected.
- Lookup authentication strength (accepted risk): Section 5's two lookup modes compose into a single-factor guarantee, not a two-factor one — phone-only mode (required, since a customer may not have their request ID) returns the request ID needed to then use ID+phone mode, so a phone number alone is sufficient to eventually retrieve a request's full detail (issue description and signed photo URLs), given both modes are required features. This is an accepted, deliberate trade-off, not an oversight: closing it would require a product change (e.g. a one-time code, or dropping the phone-only mode) that Section 5 doesn't call for, and Section 6 already excludes bot/rate-limit protection from scope. Anyone deploying this beyond the current exercise should treat "phone number" as the effective sole credential protecting a customer's request detail and weigh that against the sensitivity of what's collected.
- Abuse protection (accepted risk): Section 6 already excludes spam/bot protection (CAPTCHA, honeypot, etc.) from this exercise's scope, and that decision extends to rate limiting — neither endpoint throttles repeated requests. Concretely, this means `/api/lookup` can be queried repeatedly to harvest which phone numbers have requests (compounding the lookup authentication risk above), and `/api/requests` can be submitted repeatedly to fill the database and photo storage with no cost or lockout. Genuinely closing this needs new infrastructure (e.g. a shared rate-limit store, since serverless functions don't share in-process memory across instances) and is out of scope for this exercise, consistent with Section 6. Anyone deploying this beyond the exercise should add rate limiting before real customer phone numbers and photos flow through it.
- API key management: All secrets (GITHUB_TOKEN, SUPABASE_ACCESS_TOKEN, VERCEL_TOKEN, OPENAI_API_KEY) are stored in a local `.env` file, which is excluded from version control via `.gitignore` and is never committed, printed, or shared. Note: `SUPABASE_ACCESS_TOKEN` is a management-API token used only for CLI/project-admin operations (Development unit 2); it is not sufficient for the app's Supabase JS client. Once the Supabase project exists, its connection values (project URL, anon key, service-role key) must also be added to `.env` under the same never-commit rule.
- Photo access: Uploaded repair photos are stored in a private Supabase Storage bucket and served only via signed, expiring URLs — not publicly accessible.
- Data retention: No automatic deletion is implemented in this exercise; repair requests and photos are kept indefinitely. A retention/cleanup policy will be revisited post-launch.

## 8. Technology stack
- Next.js — handles the screen and the server-side code (API) in one project
- Supabase — stores repair request records and uploaded photos (matches the `SUPABASE_ACCESS_TOKEN` already provisioned in `.env`)
- Reason it's fixed: it's the same setup used in the Part 1–2 practice, and we'll deploy to Vercel in Part 5, so this keeps everything continuous

---

## 9. Development units
1. Scaffold the Next.js project and load the existing `.env` values.
2. Create the Supabase project and connect it using `SUPABASE_ACCESS_TOKEN`.
3. Create the `repair_requests` database table (request ID, device type, `device_type_other` for the free-text "Other" value, issue description, phone number, photo paths, status, timestamps) and a `status_history` table (request ID, status, changed_at) to log each status change; add a database trigger that inserts into `status_history` whenever a request is created **or** its status changes (including manual edits made directly through the Supabase dashboard, since there's no admin UI — see Section 6 out-of-scope), so the initial "Received" stage is captured automatically too, not just later transitions.
4. Create a private Supabase Storage bucket for repair photos, served via signed URLs.
5. Build the Repair Request Submission form UI (device type dropdown, issue description, phone number, photo upload).
6. Build the API route to validate and save a new request, auto-generate the `RPR-######` request ID, and set status to "Received."
7. Build the photo upload handling (max 3 files, JPG/PNG only, 5MB each, validated server-side) into Supabase Storage, and save the resulting storage paths onto the `repair_requests` row.
8. Build the Repair Status Tracking lookup form UI (request ID + phone number inputs).
9. Build the API route for status lookup: request ID + phone number returns the single matching record; phone number alone returns the multiple-matches list.
10. Build the status display UI showing the current stage (Received → In Repair → Ready for Pickup → Completed).
11. Add form validation and error messages for both the submission and lookup forms.
12. Deploy the app to Vercel using the default `*.vercel.app` subdomain (no custom domain for this exercise) and configure the production environment variables.
